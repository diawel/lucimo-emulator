# 解析の記録

lucimo リモコン（VENTOTA Minoi CGY / LUC-RC-01）の電波を解析したときの作業ログです。
使い方は[リポジトリ直下の README](../README.md) にあります。

> [!CAUTION]
> 実験の一部は AI エージェントに実施と記録をさせたもので、再検証していない結論を含みます。
> 数値や「確定」「検証済み」と書かれた箇所も、作者の手元の1台で一度確かめた結果にすぎません。
> 参考として読み、根拠にするときは自分の環境で確かめてください。

このディレクトリには、解析にだけ使ったツールも置いています。

- `ble_hci/`：生の HCI でアドバタイズを送る実験用ファーム。ルートの `lucimo.py` の送信サブコマンド（`python3 lucimo.py ON` など）はこのファーム向けで、現行の `lucimo_server` では動きません。
- `cam/`：カメラ映像の輝度から照明の反応を自動判定するページ一式。`python3 cam/serve.py` を起動して Chrome で `localhost:8765` を開き、照明をドラッグで囲みます。
- ルートの `clone.py`：フレームからアドレスとアドバタイズデータを逆算する解析スクリプト。前半の関数は `lucimo.py` と `genframes.py` が読み込んでいるので、ルートに残しています。

現行ファームにも解析用の口が残っています。`/raw?d=<62文字hex>&ms=400` で任意の AdvData を送れ、`/cmd` に `&t=<番号>` を付けると連番列を使わずに指定トークンを送ります。

## プロトコル

リモコンは **BLEアドバタイズ**を 2402MHz(ch37) の1波だけで送出する（ch38/39には何も出ていない）。
AA=0x8E89BED6 / ADV_NONCONN_IND / ランダムアドレス / AdvData = Manufacturer Specific Data
（企業ID 0x5556、先頭4バイトは常に `F0 08 10 00`）。ホワイトニングもCRC-24もBLE標準。

1押下で2種類のフレームが1:1で飛ぶ。
- **P** … 命令の実体。**これだけ送れば動く**。先頭16バイト固定、以降が毎回変化
- **Q** … カウンタ(frame[28])や命令バイト(frame[22]=10:ON/11:OFF)が平文で見えるが、**送っても動かない囮**

## リプレイ防御＝ローリングコード（確定）

**照明はローリングコードで守られている。** 内部に期待カウンタを持ち、
**アイドル後の最初の1枚は無条件で受け入れて同期し、以降はカウンタが進む順でないと拒否する。**

決め手の実験（2026-10-01、`/raw` で経路・タイミングを揃え、カメラで輝度を監視）:

- 実機の**連続トリプル**（お好み②→ナイト→お好み② を1秒おき、カウンタ N,N+1,N+2）を
  0.2/0.5秒で撃ち返すと、**3段すべて通る**。採取から1日超でも通る（＝実時間的な古さは無関係）。
- まったく同じ3枚を**逆順**に撃つと、**最初の1枚だけ通り、残りは拒否**される
  （真ん中のナイトの「暗転の谷」が消える）。中身は同一で順序だけの差なので、
  判定しているのは**同期点からの連番性**だと確定。
- 寄せ集めの保存トークンは、カウンタが飛び飛びなので連続で撃つと2枚目以降で落ちる
  （順序を入れ替えても対称に落ちる＝大小順ではなく連番が要る）。

以前「11秒の時間制限」と読んでいたのは、**アイドル後の再同期までの間隔**のこと。
同じトークンを撃ち直すとカウンタが進まないので、再同期するまで（≒11秒台）は弾かれる。
時間ではなく「同期点を過ぎて次の連番が来たか」で決まる。平文の手がかりとして、
Q(囮)フレームの frame[28] にカウンタが見えている。

### カウンタの受理条件（実測）

照明の内部カウンタ（全ボタン共通の通し番号）に対して、撃ったフレームの受理条件:

| 相対位置 | 判定 |
|---|---|
| 後退（高水位より小さい） | 拒否 |
| 同一（同じトークンの再送） | 拒否（進まないので） |
| **前方 +1〜+33** | **受理** |
| 前方 +34 以上 | 拒否 |
| アイドル約16秒後の最初の1枚 | 無条件受理（高水位をそこへ再同期）→ 窓が復活 |

**前方ウィンドウ = 33**。42個の連番Pを採り、P\[0\]→P\[g\] と飛ばして撃って境界を特定した
（g≤33 受理、g=34 拒否）。押し逃し耐性のための、よくあるローリングコードの前方窓。

### 実用上の帰結と連打対応の設計

- **普段使い（1ボタンずつ、十数秒おき）は保存トークンのままで確実。**
  各押下が「アイドル後の最初の1枚」になり、毎回再同期して通る。ボタンごと1個でも足りる。
- **高速連打を効かせるなら「全ボタンを1周ずつ、M周」採る。**
  カウンタは全ボタン共通なので、1周（21ボタン）ぶん採ると同じボタンの隣は約21離れる。
  窓33 > 21 なので、次の周の同じボタンへ飛んでも受理される。M周採れば同じボタンを
  最大M回まで高速連打でき、アイドル約16秒で窓が復活して撃ち直せる。家庭用途はM=3〜5周で足りる。
  → 旧「N個あればN連打」モデルは誤り。要るのは個数ではなく**連番の並び**。採取は
  `harvest.py` ではなく時刻順を保つ採り方にする（WATCHの出力をそのまま順序付きで保存）。

### 実装（2026-10-01、全ボタン完了）

連番の順送り再生を実装し、全21ボタンに展開した。実測で検証済み：
ON/OFF高速トグル 24/24・見送り0、FAV2↔ナイトの高速交互 8/8・見送り0。

- **データ**: `frames.json` の `SEQ_ALL` = `[[ボタン名, フレーム], ...]` を**カウンタ順**に持つ1本の列。
  `genframes.py` が `SEQ[]`（トークン）＋ `SEQCMD[]`（各トークンの命令ID）＋ `NSEQ` を生成する。
- **ファーム** (`seqPlay`): グローバルなポインタ `seqPos` を**前にだけ**進め、要求ボタンの
  次のトークンを撃つ（末尾まで無ければ先頭へ巻き戻す）。約16秒アイドルで `seqPos` を先頭へ戻す。
  `/cmd`・本体ボタンとも全ボタンがこの経路。SEQに無いボタンだけ従来の `txStart` へ落ちる。
- **見送り(busy)は無し**（実験の結果こうした）。窓を超えた／巻き戻しのトークンは照明が静かに弾く
  だけで、ブリックも固着もせず、押し続ければ再同期して回復する。`/busy` を待つUIより素直。
  **回復は「送る」ことで起きる。沈黙では戻らない**（実測: 高カウンタ後の沈黙1〜3秒では後退
  フレームは拒否、別フレームを撃ち続けると受理＝回復）。旧「無駄撃ちが回復を遠ざける」はローリング
  コードでは当てはまらない。別軸で「最近見たトークンを約11秒弾く」重複キャッシュもある。
- **採取**: 全21ボタンを決めた順で1周、それをM周。**1本のWATCHセッションで連続して**採り、
  周の間は3秒ほど空ける（`gap>2.5s` で周を切り分け、ちょうど21個の周だけ採用）。21個でない周は捨てる。

**落とし穴（重要）**: `SEQ_ALL` は**ひと続きのカウンタ列**でなければならない。採取時期の違う列
（例: 数時間前のON/OFFバースト＋今の周回）を混ぜると、境目のカウンタ段差が窓33を超え、そこで
順送りが詰まる（`busy` が出て先に進めない）。必ず、間に実機を押していない連続した周回だけで1本にする。

**ONは「直前状態の復元」**: 全点灯ではなく、消灯直前の明るさ・色に戻す（FAV2直後のONは明、
ナイト直後のONは暗）。カメラ検証で「ONは常に明」と決めつけない。`REST`/`MAXWAIT` は旧ロジックの
名残で、ON/OFF以外のSEQ未整備時のフォールバックにのみ効く。

UI・本体ボタンとも **250ms・無音なし** に統一（`ONCE_MIN` / `btnMinMs`）。
押してから照明が反応するまで約0.25秒。送信時間は400msで十分（1000msと差なし）。

### 長押しは単発で代用（1タップ = 1段階）

実機は長押し中、**0.2秒ごとに新しいトークン**を出す（3秒の長押しで約15個、連番）。
ローリングコードなので連番の実トークンでないと追随できない。採取済みの寄せ集めでは不可。
よって **明るく/暗く/白色/暖色も単発**にしてある。10個持てば10段階を素早く動かせる
（各段が再同期前提の単発）。

## トークンの改変は受け付けられない

ペイロードは Service Data (UUID 0x08F0) の `10 00` に続く22バイト。押下ごとに全体が変わる。

未使用トークンを基準に**1バイトずつ反転して送る実験**を22箇所すべてで行った結果、
**無改変は反応し、どの1バイトを変えても無反応**。22バイト全体に署名が付与されており、照明がそれを検証していると考えられる。
署名の作り方は分かっていないので、このリポジトリは実機から採取したトークンを再生する方式をとる。
ローリングコードなので、連打を効かせたい場面では**連番の並びごと**採取して順送りに撃つ。

（20サンプル中、3・17・18回目が16/22バイト一致するという構造は見えるが、
署名を作るのに使える手がかりではなく、内部状態が近かった結果と考えられる）

## 技術メモ

- ホワイトニング: x^7+x^4+1, ch37 シード 0x65
- CRC-24: poly 0x65B / init 0x555555（実装は反転表現なので 0xAAAAAA と書く）
- BLEコントローラ経由で出せるのは frame[0..37]。CRC(frame[38..40])はコントローラが付け、実機と一致する
- 送信間隔は**生HCIなら5ms**（151発/秒）。正規BLE APIは下限20msで約50発/秒しか出ず不足する。
  2.5msはコントローラが拒否して31発/秒に落ちる
- 送信時間の下限は実測 200ms（10/10）。120ms=4/10、80ms=0/10 と急に崩れるので **250ms** を既定にした
- **送信前の無音は不要**。実機にもそんな区切りはない。かつて入れていた400msは仕組みごと廃止した
- レート制限・ロックアウトは存在しない
- WiFiとBLEの競合は無実（WiFiを完全に止めても挙動は変わらない）

## 落とし穴（何度も嵌った）

- **frames.h は frames.json から生成する。手で compile すると古い表のまま焼け、空撃ちになる。必ず build.sh**
- **スニファのnRF24は時々 connected=0 に落ちる**。測定前に必ず `REINIT` を入れること（DIAGで確認できる）
- スニファの TALLY は上位数件しか保持しない。周囲のBLEに押し出されて目的のフレームが消えるので、
  特定フレームを数えるときは**そのフレーム自身の frame[16..20] を同期語にする**
- 命令の合間に計測待ちを入れると「間隔0秒」が実際には数秒あく。間隔を測るときは撃つ間は眠らず、
  輝度ログから後で遡って計算する
- pkill のパターンは起動コマンド全体に一致する。測定サーバまで巻き込んで止めないこと
